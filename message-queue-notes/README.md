메시지 큐(Message Queue, MQ)
=================

1\. 정의
-------------------
```
메시지 큐는 프로세스 간 데이터 통신(IPC)이나 서비스 간 통신에서 비동기(Asynchronous) 방식으로 메시지를 주고받기 위한 중간 매개체입니다.
```

2\. 왜 사용하는가? (핵심 가치)
-------------------
```
1) 비결합도(Decoupling): 송신자(Producer)는 수신자(Consumer)가 현재 살아있는지, 바쁜지 알 필요가 없습니다. 
                       큐에 던지기만 하면 자기 할 일을 할 수 있습니다.
2) 부하 분산(Load Balancing / Smoothing): 갑자기 트래픽이 몰릴 때, 메시지 큐가 '댐' 역할을 하여 뒷단 서버가 감당 가능한 속도로 
                                        메시지를 가져가 처리하게 합니다.
3) 탄력성(Resiliency): 수신 서버가 잠시 죽더라도 메시지는 큐에 안전하게 보관되므로 데이터 유실을 방지할 수 있습니다.
4) 비동기 처리: 사용자의 요청에 즉각적인 응답이 필요 없는 작업(예: 메일 발송, 대규모 데이터 집계)을 백그라운드로 돌려 사용자 경험을 개선합니다.
```

3\. 메시지 전송 모델
-------------------
```
모델                              설명                                                     특징
P2P (Point-to-Point)            한 명의 생산자가 던진 메시지를 한 명의 소비자가 가져감            일대일 통신, 작업 할당(Job Queue)에 적합
Pub/Sub (Publish/Subscribe)     한 명의 발행자가 메시지를 던지면 구독 중인 모든 소비자에게 전달    일대다 통신, 이벤트 알림 등에 적합
```

5\. 실무 적용 시 주의사항 (Anti-Patterns)
-------------------
```
1) 메시지 순서 보장: 분산 환경에서 여러 컨슈머가 메시지를 가져갈 때, 발생 순서대로 처리되지 않을 수 있음을 설계에 반영해야 합니다.
2) 중복 처리(Idempotency): 네트워크 장애 등으로 인해 같은 메시지가 두 번 전달될 수 있습니다. 따라서 컨슈머 로직은 멱등성을 유지하도록 짜야 합니다.
3) 독약 메시지(Poison Message): 특정 메시지가 계속 에러를 유발해 시스템을 마비시키지 않도록 별도의 '에러 큐(Dead Letter Queue)' 처리가 필요합니다.
```

6\. 기본 컴포넌트
-------------------
```
1) Producer : 메시지를 생성해서 큐에 전송하는 주체로 비즈니스 로직을 수행한 후에 그 결과를 메시지 형태로 발행하는 역할을 맡습니다.
2) Consumer : 큐에서 메시지를 가져와서 처리하는 역할을 담당하며 독립적으로 메시지를 소비하고 필요한 작업을 수행합니다.
3) Broker(중개자)  : 프로듀서랑 컨슈머 사이에서 메시지를 저장하고 전달하는 중앙 서버 (ex. kafka, AWS SQS)
                    메시지의 저장, 전달 보장 등의 핵심 기능을 제공합니다.
```

7\. 메시지 보존 방식
-------------------
```
1) 메모리  : 메시지를 RAM에만 저장해서 매우 빠른 속도를 제공하지만, 브로커가 중단이 되면 메시지가 손실될 수 있습니다.
            redis나 rabbit MQ 같은 기본 모드가 이에 해당하며 처리 속도가 중요하고 일부 메시지 손실이 허용되는 경우에 사용됩니다.
2) 디스크  : 디스크 기반 영속성은 메시지를 디스크에 저장하여 브로커 재시작 후에도 데이터를 보존합니다. 예를 들어 kafka는 모든 메시지를 디스크에 
            순차적으로 기록하며 설정된 보존 기간 동안 메시지를 유지합니다. 이 방식은 약간의 성능 오버헤드가 있지만 데이터 손실을 방지하고 재처리가 
            가능해서 금융거래나 주문 시스템 같은 중요한 데이터를 다룰 때 필수적입니다.
```

8\. 메시지 처리 모델
-------------------
```
1) Push모델   : 브로커가 능동적으로 컨슈머들에게 메시지를 전송하고 컨슈머는 준비 상태를 항상 유지합니다. 그리고 메시지를 즉시 받아서 처리합니다.
               지연 시간이 짧고 실시간 처리에 유리하긴 하지만 이 컨슈머의 처리 능력을 초과하는 메시지가 밀려서 들어올 경우에는 과부하가 발생할 수
               있습니다.
2) Pull모델   : 컨슈머가 브로커에게 메시지를 요청해서 가져오는 겁니다. (kafka) 컨슈머가 자신의 처리 속도에 맞춰서 메시지를 가져오기 때문에
                이 메시지가 밀려 들어와서 힘들어하는 상황이 없다. 이 컨슈머는 배치 단위로 메시지를 가지고 와서 효율적으로 처리 할 수 있다.
                처리 속도가 느린 컨슈머들도 자신의 페이스를 유지할 수 있다. 폴링할 때 빈응답이 올 수도 있고 실시간성이 Push모델보다 약간
                떨어질 수 있다.
    * 컨슈머가 주기적으로 메시지를 가져오는 작업을 폴링 작업이라고 한다.
```

9\. 큐 타입
-------------------
```
1) Standard Queue   : 순서가 중요하지 않은 시스템에서 사용한다. (이메일 발송, 로그수집, 통계성 데이터 수집, 알림)
2) FIFO Queue       : 내부적으로 순서를 추적하기 위해서 시퀀스 번호를 사용한다. 중복 제거를 위해서 메시지 아이디 같은 것을 활용한다.
                      (주문 생성, 결제, 재고 차감, 배송 준비)
```

10\. DLQ(Dead Letter Queue)
-------------------
정상적으로 처리할 수 없는 메시지를 격리하여 보관하는 특별한 큐
```
DLQ 인입조건    : 예외발생, 최대 재시도 횟수 초과, 메시지 형식이 잘못된 경우 등
문제 있는 메시지가 반복적으로 재처리되면서 시스템 리소스를 낭비하거나 정상 메시지 처리를 방해하는 것을 방지합니다.
원본 메시지 내용, 실패 시각, 에러 메시지, 재시도 횟수 등의 메타 데이터와 함께 보관됩니다.
```

네트워크 이론: Store-and-Forward
네트워크 통신 기술 중 '축적 전송(Store-and-Forward)' 방식도 중요한 뿌리입니다. 데이터를 목적지로 바로 보내는 것이 아니라, 중간 노드(큐)에 일단 저장했다가 다음 노드로 보낼 준비가 되었을 때 전달하는 방식입니다. 이 개념 덕분에 네트워크가 불안정해도 데이터 손실을 방지할 수 있게 되었습니다.
