GOAL
======================

1\. 목표
--------------
```
1) 단순히 에러 로그를 긁어오는 수준이 아니라, '감지 - 분류 - 알림 - 사후 관리'의 라이프사이클을 자동화하는 것이 핵심입니다.
2) 장애 인지 시간(TTD, Time To Detect): 기존(사용자 신고 후 확인) 30분 -> 시스템 감지 1분 이내.
3) 장애 분석 효율: 에러 발생 시 로그 서버에 접속해 수동으로 뒤지는 시간을 제거하여 분석 시간 70% 단축.
```

2\. 전송 데이터
--------------
```
에러 발생 시간, 서버명, 서비스명, 에러 메시지 전문, 그리고 앞뒤 10줄 정도의 Context 로그를 함께 보내면 분석에 매우 유리합니다.
```

3\. 결정적 한 끗
--------------
```
1) 비동기 처리 (Asynchronous): 로그를 읽고 API를 호출하는 과정이 원래 서비스 프로그램의 성능에 절대 영향을 주면 안 됩니다. 반드시 
   별도의 스레드나 큐(Queue)를 사용하여 독립적으로 실행되게 만드세요.
2) 로그 유실 방지 (Reliability): 네트워크 장애로 API 호출이 실패할 경우, 전송하지 못한 로그를 로컬에 임시 저장했다가 재전송하는 
   Retry 로직이 필수입니다.
3) 개인정보 마스킹: 로그에 포함된 계좌번호나 이름 등을 API로 쏘기 전 자동 마스킹하는 기능을 넣으세요. 보안 부서의 승인을 받는 핵심 
   포인트가 됩니다.
```

4\. 과정
--------------
```
2) 개발하시려는 시스템의 핵심 메커니즘은 '로그 테일링(Log Tailing)'과 '패턴 매칭(Pattern Matching)'입니다.
3) 금융권에서는 "정상적인 에러(예: 잘못된 비번 입력 등)"와 "진짜 장애(예: DB Connection Pool 고갈)"를 구분하는 것이 중요합니다. 
   에러 화이트리스트/블랙리스트 관리 기능을 넣어 불필요한 알람을 줄여야 평가단에게 인정받습니다.
```

5\. 에이전트 방식이 가벼운 이유
--------------
```
에이전트가 24시간 내내 CPU를 풀가동하는 것이 아니라, 'OS 이벤트 방식'을 사용하기 때문입니다.
Inotify (Linux 커널 기능) 활용: 에이전트가 직접 파일을 계속 뒤지는 게 아니라, OS에게 "이 로그 파일에 새 글이 써지면 나를 깨워줘"
라고 부탁하는 방식입니다. 글이 써지기 전까지 에이전트는 '대기(Idle)' 상태로 메모리만 아주 조금(수십 MB) 차지하며 잠들어 있습니다.
리소스 격리: 에이전트는 온라인 업무 서비스(WAS)와 별도의 프로세스로 동작합니다. 만약 에이전트에 문제가 생겨도 업무 서비스가 죽지는 
않습니다.
```

6\. 테이블 설계
--------------
```
(1) 로그 마스터 테이블 (TB_ERR_LOG_MST)         : 에러의 전체적인 현황을 관리합니다.
ERR_ID (PK, 시퀀스)
SVR_NM (서버명: 온라인A, 배치B 등)
LOG_PATH (로그 파일 경로)
ERR_LEVEL (ERROR, WARN 등)
REG_DT (발생 및 등록 일시)

(2) 로그 상세/멀티라인 테이블 (TB_ERR_LOG_DTL)     : 긴 Stack Trace나 상세 내용을 저장합니다.
ERR_ID (FK)
ERR_MSG_FULL (CLOB 타입: 에러 원문 전체)
ERR_MSG_SHORT (핵심 에러 메시지만 추출)

(3) 장애 조치 가이드 테이블 (TB_ERR_KNOWLEDGE)    : 키워드와 조치 방법을 매칭합니다.
KWD_ID (PK)
MATCH_KWD (매칭될 키워드나 SQL 에러 코드)
REMEDY_DESC (조치 방법 가이드)
```
