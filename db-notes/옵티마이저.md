데이터베이스 옵티마이저
=============

3\. 정의
--------
```
사용자가 입력한 SQL을 가장 효율적으로 수행할 수 있는 최적의 처리 경로(Execution Plan)를 찾아내는 DBMS의 핵심 엔진입니다.
```

4\. 영향
--------
```
동일한 결과를 내는 SQL이라도 어떤 경로로 데이터를 읽고 조인하느냐에 따라 성능이 수십 배 이상 차이 나기 때문에, 옵티마이저의 역할은 
데이터베이스 성능에 절대적인 영향을 미칩니다.
```

5\. 옵티마이저의 주요 작동 단계
--------
```
1) SQL 파싱 및 변환 (Parser & Query Rewriter): SQL 문의 문법을 검증하고, 의미가 같지만 더 효율적인 형태로 쿼리를 재작성
                                             (예: 불필요한 뷰 머징, 서브쿼리 최적화)합니다.
2) 비용 산정 (Cost Estimator): 테이블 크기, 인덱스 분포도, 컬럼 히스토그램 등의 통계 정보를 바탕으로 각 실행 계획별 예상 
                             비용(CPU 사용량, I/O 횟수 등)을 계산합니다.
3) 실행 계획 생성 (Plan Generator): 후보군 중에서 가장 비용이 적게 드는(효율적인) 최적의 실행 계획을 최종 선택하여 쿼리를 실행합니다.
```

6\. 비용 기반 옵티마이저 (CBO, Cost-Based Optimizer)
--------
현재 상용 및 오픈소스 RDBMS(Oracle, MySQL, PostgreSQL 등)의 표준은 CBO 방식입니다.
```
1) 통계 정보를 기반으로 데이터의 분포도(Cardinality)와 선택도(Selectivity)를 예측합니다.
2) 인덱스의 유무, 데이터 건수, 하드웨어 성능 등을 종합적으로 고려해 비용을 산출합니다.
3) 주의점: 테이블 데이터가 급격히 변경되었음에도 통계 정보가 최신 상태가 아니거나 왜곡되어 있다면, 옵티마이저가 잘못된 판단을 내려 
          비효율적인 실행 계획(예: 인덱스를 탈 수 있는데 풀 스캔을 유발)을 선택하는 성능 저하가 발생할 수 있습니다.
```

5\. 주요 액세스 경로 및 조인 방식
--------
```
1) Full Table Scan (FTS): 테이블 전체를 처음부터 끝까지 읽는 방식. 데이터의 양이 매우 적거나 전체 데이터의 상당 부분을 조회할 때 
                          유리합니다.
2) Index Scan / Range Scan: 인덱스를 통해 필요한 데이터만 효율적으로 찾아가는 방식. 조건에 맞는 소량의 데이터를 조회할 때 
                            필수적입니다.
3) 조인 알고리즘:
 - Nested Loop Join (NL Join): 선행(Driving) 테이블의 결과 건수만큼 반복해서 후행 테이블을 찾아가는 방식 (OLTP 환경, 소량 
                               데이터 조인에 적합).
 - Hash Join: 해시 테이블을 메모리에 생성한 뒤 조인 키를 기준으로 매칭하는 방식 (대용량 데이터 조인에 적합).
 - Merge Join: 양쪽 테이블을 각각 정렬한 뒤 순차적으로 비교하며 조인하는 방식.
```

6\. 옵티마이저 성능 관리를 위한 핵심 요소
--------
```
1) 통계 정보 수집: 주기적인 통계 정보 갱신을 통해 옵티마이저가 실제 데이터 상태를 정확히 반영하게 유지합니다.
2) 실행 계획 분석: EXPLAIN (또는 EXPLAIN ANALYZE) 명령어를 활용해 옵티마이저가 어떤 방식으로 쿼리를 처리하는지 모니터링합니다.
3) 힌트(Hint) 사용: 옵티마이저가 최적의 경로를 찾지 못할 경우, 개발자가 직접 특정 인덱스나 조인 방식을 지정하도록 유도할 수 있습니다.
```
