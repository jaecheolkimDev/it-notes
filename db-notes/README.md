DB 공부 노트
=============

1\. 개념
--------
```
- 인덱스 : 데이터를 빨리 찾기 위해 특정 컬럼을 기준으로 미리 정렬해놓은 표
  - 클러스터링 인덱스 : PK
  - 고유 인덱스 : Unique
  - 멀티 컬럼 인덱스 : 2개 이상 컬럼
    - 컬럼의 순서는 매우 중요하다.
    - 처음에 배치된 컬럼들은 일반 인덱스처럼 활용할 수 있다.
    - 구성할 때 데이터 중복도가 낮은(=카디널리티가 높은) 컬럼이 앞쪽으로 오는 게 좋다.
  - 커버링 인덱스 : SQL문을 실행시킬 때 필요한 모든 컬럼을 갖고 있는 인덱스
- SQL 튜닝
  - 필요한 이유 : 옵티마이저가 세운 계획이 완벽하지 않기 때문에 힌트로 조정해줘야함.
- 실행계획 : 옵티마이저가 SQL문을 어떤 방식으로 어떻게 처리할 지를 계획한 걸 의미
- 아우터조인 : (+)가 붙은쪽은 값이 없어도 결과에 포함되서 나옴.
  -(+)가 붙은쪽 기준으로 반대가 left인지 right인지에 따라서 left outer join / right outer join
  
마이그레이션의 영어 뜻 : 이주
실제 마이그레이션의 의미는 대부분 여러 DB를 하나의 DB로 합치거나 현재 DB를 타 DB로 옮기는 경우 등을 의미한다.
실 예제로 차세대 프로젝트 시 기존 DB를 타 DB로 변경하거나 통합시스템 구축 시 여러 DB를 하나의 DB로 합치는 것이 마이그레이션의 예가 된다.

인라인뷰 INLINE VIEW : SELECT절의 결과를 FROM절에서 하나의 테이블처럼 사용하고 싶을 때 사용한다.
서브쿼리 SUB QUERY : SELECT절의 결과를 WHERE절에서 하나의 변수(상수)처럼 사용하고 싶을 때 사용한다.
스칼라 서브쿼리 SCALAR : SELECT절에 서브쿼리를 사용하여 하나의 컬럼처럼 사용하고 싶을 때 사용한다.

- 테이블 스페이스  : 데이터가 저장되는 공간
    - ORA-01653 : 테이블스페이스에서 확장할 수 없습니다.
```

2\. 인덱스 스캔
-----------
```
- 풀 테이블 스캔(Full Table Scan) : 인덱스를 활용하지 않고 테이블을 처음부터 끝까지 전부 다 뒤져서 데이터를 찾는 방식
- 풀 인덱스 스캔(Full Index Scan) : 인덱스 테이블을 처음부터 끝까지 다 뒤져서 데이터를 찾는 방식
- const : 조회하고자 하는 1건의 데이터를 헤매지 않고 단번에 찾아올 수 있을 때 const가 출력된다.
  - 고유 인덱스 또는 기본 키를 사용해서 1건의 데이터만 조회한 경우
- 인덱스 레인지 스캔(Index Range Scan) : 인덱스를 활용해 범위 형태의 데이터를 조회한 경우를 의미한다.
  - 범위 형태란 BETWEEN, 부등호(<, >, ≤, ≥), IN, LIKE를 활용한 데이터 조회
- ref : 비고유 인덱스를 사용한 경우
  - UNIQUE가 아닌 컬럼의 인덱스를 사용한 경우
```



3\. 홑따옴표
--------
```
- 홑따옴표
  ORA-00911 오류는 Oracle 데이터베이스에서 SQL 구문이 문법적으로 잘못되었을 때 발생하는 오류입니다. 특히 쿼리문에 부적절한 문자(주로 세미콜론;)나 홑따옴표(‘) 등의 특수문자가 포함되어 있을 때 발생하며, 쿼리문에서 해당 문자를 제거하거나, XML 등에서 홑따옴표를 이스케이프(escape) 처리하여 해결할 수 있습니다.
  JAVA 데이터 DB 입력 시 '(홑따옴표)로 인한 오류 해결 방법
  Java 파일로 request한 데이터를 받아서 DB에 입력하는 과정에서 '(홑따옴표)로 인해서 DB에 입력 시 Syntax error가 발생하는 경우가 있다. 이러한 문제는 replaceAll로 '(홑따옴표)를 &#39로 치환해서 DB로 입력하도록 하면 해결 할 수 있다.
  String Data = request.getParameter(data);
  Data = Data.replaceAll("'","&#39;");
  '를 &#39로 치환해서 DB에 입력!

- 오라클에서 길이가 0인 데이터는 Null이다.(mysql은 공백문자가 존재함)
- 오라클 UTF-8환경에서 †(단검/dagger)특수문자는 일반적으로 3바이트를 차지합니다.(일반 특수문자는 1바이트)
```




4\. 파싱
--------
```
- 파싱 : SQL을 실행하기 전에 SQL문을 구문 분석하고 실행계획을 수립하는 과정
  - 하드 파싱 : SQL이 처음 실행됬거나 Shared Pool에 동일한 SQL이 존재하지 않아 새로 실행 계획 수립해야하는 경우
  - 소프트 파싱 : Shared Pool에 동일한 SQL 존재해서 재사용
- 하드 파싱 개선 방안
  - 1) 바인드 변수 사용으로 동일 SQL로 인식
  - 2) SQL 텍스트 통일(*불필요한 공백, 대소문자 차이, 주석제거 등으로 동일 SQL 인식률 향상*)
    - 위와 같은 방법들을 통해 소프트 파싱으로 유도해서 성능 개선
```



5\. Library Cache
--------
```
오라클 DB의 라이브러리 캐시(Library Cache)에 저장된 쿼리(SQL)는 주로 메모리 부족(LRU 알고리즘)에 따라 오래된 것부터 삭제되거나, 
데이터베이스 재시작, DDL 문(ALTER/DROP 등)에 의한 객체 변경 시 사라집니다. 
자주 사용되지 않는 쿼리는 LRU(Least Recently Used) 규칙에 의해 자동으로 비워집니다.

주요 캐시 삭제 요인
    - LRU (Least Recently Used) 알고리즘  : Shared Pool 메모리가 부족할 때, 가장 오랫동안 재사용되지 않은 쿼리부터 캐시에서 제거.
    - DDL 문 실행    : 해당 SQL이 참조하는 테이블이나 뷰가 변경(ALTER, DROP)되면 관련 캐시 항목이 무효화(Invalidate).
    - 데이터베이스/인스턴스 재시작   : 인스턴스를 내리면 메모리(SGA)의 내용이 모두 초기화.
    - 명시적 플러시   : DBA가 ALTER SYSTEM FLUSH SHARED_POOL; 명령을 사용하여 수동으로 캐시를 비울 수 있습니다.
```


6\. Oracle의 성능 향상을 위한 캐싱 메커니즘
--------
```
오라클 DB에서 첫 실행 쿼리가 느리고 두 번째부터 빠른 이유는 데이터 및 실행 계획 캐싱 때문입니다. 
처음에는 디스크(HDD/SSD)에서 데이터를 불러오지만, 이후에는 메모리(Buffer Cache, Shared Pool)에 저장된 데이터를 사용하여 
I/O 병목이 사라져 속도가 빨라지는 현상입니다. 
Buffer Cache (데이터 블록 캐싱)    : 쿼리가 처음 실행될 때 필요한 데이터 블록이 디스크에서 메모리(Buffer Cache)로 로딩됩니다. 
                                  두 번째 실행 시, 디스크 I/O 없이 메모리에서 바로 데이터를 읽기 때문에 훨씬 빠릅니다.
Shared Pool (실행 계획 캐싱)  : Oracle은 쿼리의 SQL 문장 자체를 분석(Parsing)하고 최적의 실행 계획(Execution Plan)을 세우는 데 
                             시간이 걸립니다. 
                             한번 실행된 쿼리는 라이브러리 캐시(Library Cache)에 저장되어 이후 Parsing 과정을 생략합니다.
```


7\. SQL의 3단계 논리
--------
TRUE , FALSE , UNKNOWN
```
1) NOT IN의 이슈
    (10, 20, NULL)
    WHERE A != 10 AND A != 20 AND A != NULL
    (A != NULL) => UNKNOWN
    (TRUE AND TRUE AND UNKOWN) => UNKNOWN
    논리 연산에서 하나라도 'UNKNOWN'이면 전체 조회가 마비됩니다.
        => NULL은 IS NULL, IS NOT NULL로 조회해야 정상적으로 조회됩니다.
        => NOT IN에서 NULL이 포함되어 있으면 안됩니다.
```
