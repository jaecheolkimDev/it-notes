JPA
===========================================


1\. 데이터베이스 초기화 전략 - DDL AUTO 옵션
-----------------------
```
spring.jpa.hibernate.ddl-auto 옵션을 통해 애플리케이션 구동 시 JPA의 데이터베이스 초기화 전략을 설정할 수 있습니다.
- none          : 사용하지 않음
- create        : 기존 테이블 삭제 후 테이블 생성
- create-drop   : 기존 테이블 삭제 후 테이블 생성. 종료 시점에 테이블 삭제
- update        : 변경된 스키마 적용
- validate      : 엔티티와 테이블 정상 매핑 확인
```

2\. 기본키 생성 전략 - @GeneratedValue
-----------------------
```
- GenerationType.AUTO(default)  : JPA 구현체가 자동으로 생성 전략 결정 
- GenerationType.IDENTYITY      : 기본키 생성을 데이터베이스에 위임
- GenerationType.SEQUENCE       : 데이터베이스 시퀀스 오브젝트를 이용한 기본키 생성
- GenerationType.TABLE          : 키 생성용 테이블 사용
```

3\. 연관 관계 매핑 종류
-----------------------
```
일대일(1:1)    : @OneToOne
일대다(1:N)    : @OneToMany
다대일(N:1)    : @ManyToOne
다대다(N:N)    : @ManyToMany

JPA 전략
 - JPA는 기본적으로 "혹시 데이터가 없을지도 모르니 안전하게 다 가져올게(Outer Join)"라는 마인드로 동작합니다.
   (유실 방지, 손실 방지)
 
LEFT OUTER JOIN 발생 사유
 - JPA는 해당 연관 관계의 값이 null일 가능성이 있다고 판단하기 때문입니다.(optional = true)
 
INNER JOIN으로 변경하기 위해선
 - 속성 변경    : @OneToOne(optional = false)
 - @JoinColumn의 nullable 속성 변경(위 설정도 같이해주면 성능상 좋음)
  ex) @JoinColumn(name="member_id", nullable = false)

JPA에서 1:N(일대다) 관계를 매핑할 때는 보통 양방향 매핑을 권장합니다. 부모 엔티티(Parent)에서 자식 리스트를 참조할 수 있고, 
자식 엔티티(Child)에서도 부모가 누구인지 알 수 있도록 설정하는 것이 객체지향적인 설계와 데이터 관리에 유리하기 때문입니다.
    // mappedBy: 자식 엔티티에 있는 부모 참조 필드명("parent")을 지정
    @OneToMany(mappedBy = "parent", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Child> childList = new ArrayList<>();
        // RDS_MODEL_ID 컬럼을 통해 TBL_RDS_MODEL과 연결
        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "PARENT_ID")
        private Parent parent;
        
연관관계의 주인    : 외래 키를 직접 관리하는 객체입니다. DB 테이블에 FK가 있는 곳이 주인이 됩니다.
mappedBy        : "나는 주인이 아니에요. 저쪽에 의해 매핑되었을 뿐이에요"라고 선언하는 표식입니다.
```

4\. save() 심층 분석
-----------------------
```
- 시퀀스 값 조회 시 JPA에서 SELECT FOR UPDATE를 사용하는데 save 시 ID 생성 과정에서 동시성 충돌을 막기 위한 안전장치다.

- ID가 없으면 save() 같은 내장함수를 통해 INSERT/DELETE 등이 되지 않으므로 네이티브쿼리를 사용해야함.
- INSERT하고 SELECT가 바로 안될 수도 있음.
- ENTITY에 set만 해줘도 dirtyChecking을 통해 DB가 수정됨.
```

5\. CASCADE 종류
-----------------------
단일 엔티티에 완전히 종속적이고 부모 엔티티와 자식 엔티티의 라이프 사이클이 유사할 때 활용하면 됨.
부모 엔티티가 수행하는 특정 작업(Persist, Merge, Remove 등)을 자식 엔티티에 전이시키기 위해 사용하는 속성.
```
- PERSIST   : 부모 엔티티가 영속화될 때 자식 엔티티도 영속화    (새로운 부모-자식 관계를 저장할 때)
- MERGE     : 부모 엔티티가 병합될 때 자식 엔티티도 병합  (기존 엔티티와 관련된 연관 데이터를 갱신할 때)
- REMOVE    : 부모 엔티티가 삭제될 때 연관된 자식 엔티티도 삭제  (부모와 자식 관계 한꺼번에 제거해야할 때)
- REFRESH   : 부모 엔티티를 다시 읽을때 연관된 자식 엔티티도 다시 읽음  (DB데이터와 동기화가 필요할 때)
- DETACH    : 부모 엔티티가 영속성 컨텍스트에서 분리되면 연관된 자식 엔티티도 함께 분리 (특정 엔티티를 관리에서 제외해야할 때)
- ALL       : 부모 엔티티의 상태 변화를 자식 엔티티에 모두 전이  (위 모든 작업 포함)
```

6\. 고아 객체 자동으로 제거하기(orphanRemoval = true)
-----------------------
```
영속성 전이 기능과 같이 사용하면 부모 엔티티를 통해서 자식의 생명 주기를 관리할 수 있습니다.

고아 객체   : 부모 엔티티와 연관 관계가 끊어진 자식 엔티티
 - 참조하는 곳이 하나일 때만 사용해야 한다.
 - @OneToOne, @OneToMany 어노테이션에서 옵션으로 사용하면 된다.
```

7\. CascadeType과 OrphanRemoval
-----------------------
| 항목      | CascadeType                    | OrphanRemoval                        |
|----------|--------------------------------|--------------------------------------|
| 목적      | 부모의 작업을 자식에게 전이        | 부모와 관계가 끊어진 자식을 자동으로 삭제   |
| 적용 범위 | 모든 작업 유형(PERSIST, MERGE 등) | 관계가 제거된 자식 엔티티 삭제에만 초점     |
| 사용 예   | 연관 데이터의 영속성 전이를 간소화   | 부모-자식 관계가 변경될 때 데이터 정리     |
```
### 활용 팁
1. `CascadeType`은 작업 전이를 단순화하므로 저장, 병합, 삭제 등의 작업이 많은 경우 유용.
3. 두 옵션을 함께 사용할 경우 데이터 무결성과 관리 효율성을 높일 수 있음.
    - `CascadeType.REMOVE`와 함께 사용하는 경우가 많지만, 반드시 연계해야 하는 것은 아님.
```

8\. 즉시로딩과 지연로딩(JPA에서 성능 최적화의 핵심)
-----------------------
"불필요한 조인을 막고, 내가 원하는 시점에 최적화된 쿼리를 날리기 위해서" 지연 로딩을 쓰는 것이다.
```
"데이터를 언제 가져오느냐"와 "N+1 문제"라는 더 큰 이슈가 얽혀 있습니다.

1. 즉시 로딩 (Eager Loading)개념: 엔티티를 조회할 때 연관된 엔티티도 그 즉시 함께 조회합니다.
설정: @ManyToOne(fetch = FetchType.EAGER)
특징: 한 번의 쿼리로 연관된 데이터를 다 긁어옵니다.
객체를 꺼내자마자 연관된 객체를 바로 사용할 수 있어 편리해 보입니다.

2. 지연 로딩 (Lazy Loading)개념: 연관된 엔티티를 실제로 사용할 때(메서드 호출 등) 비로소 조회합니다.
설정: @ManyToOne(fetch = FetchType.LAZY)
특징:처음 조회 시 연관된 객체 자리에는 실제 데이터 대신 프록시(HibernateProxy)라는 가짜 객체가 들어갑니다.
orderItem.getOrder().getName() 처럼 실제 필드값을 건드리는 순간 select쿼리문이 실행되는 것을 확인 할 수 있습니다.

3. 즉시로딩의 치명적인 단점들 
   단순히 조인이 걸리냐 안 걸리냐의 문제가 아니라, 실제 서비스 운영 시 심각한 문제가 발생할 수 있습니다.
① 예상치 못한 SQL 발생 
(성능 저하)즉시 로딩을 설정하면, 연관된 테이블이 수십 개 얽혀 있다면 SELECT 한 번에 수많은 테이블이 조인되어 성능이 급격히 떨어집니다.
② N+1 문제 (1번의 쿼리가 N번의 추가 쿼리를 발생시킴)
JPA에서 가장 유명한 성능 문제입니다.
만약 OrderItem 10개를 조회했으면, JPA는 우선 OrderItem 10개를 가져오는 쿼리를 한 번 날립니다.
그 후, 각 OrderItem마다 연관된 Order를 채우기 위해 추가로 10번의 쿼리를 더 날리게 됩니다. 

4. 실무에서의 정석 가이드
   실무에서는 "모든 연관관계를 지연 로딩(LAZY)으로 설정하라"는 것이 철칙입니다.
이유: 즉시 로딩은 내가 제어하기 어렵고 예측 불가능한 쿼리를 만들기 때문입니다.
해결책: 일단 다 지연 로딩으로 해두고, 만약 한 번에 조인해서 가져와야 할 때가 생기면 그때만 Fetch Join이라는 기능을 사용합니다.
요약구분즉시 로딩 (EAGER)지연 로딩 (LAZY)조회 시점엔티티 조회 시 항상 함께 조회실제 사용 시점에 조회조인 방식주로 Join 쿼리 발생 
(Left Outer Join)연관 엔티티 제외하고 단일 조회권장 사항가급적 사용 금지기본으로 사용

결론적으로: @ManyToOne이나 @OneToOne은 기본값이 즉시 로딩(EAGER)이므로, 
반드시 (fetch = FetchType.LAZY)를 명시적으로 붙여주는 습관을 들이는 것이 좋습니다. 
(반면 @OneToMany는 기본값이 지연 로딩입니다.)
```

9\. Spring Data JPA의 추상화 (Repository)
-----------------------
스프링이 추상화를 잘 해둬서 영속성 컨텍스트를 직접 다루진 않는다.
```
1) save()       => 새로운 엔티티일 때 persist()
                => 기존 엔티티일 때 merge()
2) findById()   => 영속성 컨텍스트 조회 find()
                => 없으면 DB에서 가져와서 영속 상태로 만듭니다.
3) @Transactional 끝나면   => JPA가 자동으로 em.flush()를 호출하여 영속성 컨텍스트의 변경 사항(Dirty Checking)을 DB에 반영합니다.
                          => 영속성 컨텍스트도 알아서 닫힙니다. close()
4) 수동   => 대량건은 OOM이슈로 인해 일정 단위마다 flush() 및 clear() 수행
         =>  detach() 특정 엔티티를 더 이상 영속성 컨텍스트에서 관리하고 싶지 않을 때(수정해도 DB에 반영되지 않게 하고 싶을 때) 사용합니다.
```
