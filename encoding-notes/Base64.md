Base64
======================

1\. 정의
--------------
8비트 이진 데이터(Binary Data)를 ASCII 영역의 64개 인쇄 가능한 문자(Printable Characters)로 변환하는 인코딩 방식입니다.
```
알파벳 대문자(26개), 소문자(26개), 숫자(10개)를 조합하여 $26 + 26 + 10 = 62$개의 문자를 기본 단위로 사용합니다.
```

3\. 사용되는 문자 구성 (총 64개 + 패딩)
--------------
Base64는 화면에 표시할 수 있고 시스템에 독립적인 safe 문자 64개를 사용합니다.
```
1) 알파벳 대문자 (A-Z): 26개 (인덱스 0~25)
2) 알파벳 소문자 (a-z): 26개 (인덱스 26~51)
3) 숫자 (0-9): 10개 (인덱스 52~61)
4) 특수문자 (+, /): 2개 (인덱스 62, 63)
5) 패딩 문자 (=): 데이터의 길이를 맞추기 위해 끝에 붙이는 보충 문자
```

1\. 왜 Base64를 사용할까? (필요성)
--------------
컴퓨터 네트워크, 특히 이메일(SMTP)이나 초기 웹 프로토콜은 원래 7비트 ASCII 텍스트만 다루도록 설계되었습니다.
```
1) 이진 데이터(이미지, 실행 파일 등)의 제어 문자의 오작동: 바이너리 데이터 안에 들어있는 NULL, 개행문자(CR/LF), EOF(End of File) 
   같은 값들을 네트워크 장비가 "아, 데이터 전송이 끝났구나!" 하고 오해하여 통신을 끊어버릴 수 있습니다.
2) 시스템이나 네트워크 장비(라우터, 메일 서버)마다 특수 제어 문자를 해석하는 방식이 달라, 데이터를 전송하는 도중 값이 변형되거나 
   유실될 위험이 있습니다.
3) Base64는 모든 시스템이 공통으로 지원하는 64개 문자로만 데이터를 재구성하여, 전송 과정에서 데이터가 변형되거나 깨지는 것을 
   방지(전송 신뢰성 확보)합니다.
```

1\. 동작 원리 (변환 과정)
--------------
```
Base64는 3바이트(24비트)의 이진 데이터를 6비트씩 4개로 쪼개어 변환합니다. ($2^6 = 64$이므로 6비트면 64개의 문자를 표현할 수 있습니다.)
예시: 텍스트 "Man"을 Base64로 변환
1) ASCII 코드 변환:
    'M' = 77 (01001101)
    'a' = 97 (01100001)
    'n' = 110 (01101110)
2) 24비트 결합: 010011010110000101101110
3) 6비트씩 4개로 분할:
    010011 (19) -> Base64 색인표 기준 T
    010110 (22) -> W
    000101 (5)  -> F
    101110 (46) -> u
4) 결과: "Man" -> TWFu
```

1\. 용량이 늘어나서 발생하는 실제 문제점
--------------
```
실제로 개발 환경에서도 Base64의 용량 증가 문제는 늘 고려 대상입니다.
1) 대용량 파일 전송에는 부적합: 100MB짜리 영상을 Base64로 인코딩하면 약 133MB가 됩니다. 따라서 대용량 파일은 Base64 대신 
                            Multi-part/form-data나 바이너리 스트리밍 방식을 사용합니다.
2) 웹 성능 영향: 이미지 파일을 CSS나 HTML 안에 Base64로 직접 넣으면(Data URL), HTTP 요청 횟수는 줄어들지만 HTML/CSS 파일 자체가 
               커져서 초기 로딩이 느려질 수 있습니다. (보통 몇 KB 이하의 아주 작은 아이콘/이미지에만 제한적으로 사용합니다.)
```

3\. 패딩(Padding)의 역할 (=)
--------------
```
데이터가 항상 3바이트 단위로 딱 떨어지지는 않습니다.
 - 1바이트 남을 때: 6비트 2개로 나누고, 부족한 비트는 0으로 채운 뒤 끝에 ==를 붙임
 - 2바이트 남을 때: 6비트 3개로 나누고, 부족한 비트는 0으로 채운 뒤 끝에 =를 붙임
```

1\. 주요 활용 사례
--------------
```
1) 웹(Data URL Scheme): Small 이미지나 폰트 파일을 CSS/HTML에 직접 내장할 때
    <img src="data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAA..." />
2) 이메일 첨부파일 (MIME): 이메일 규격에서 이미지나 문서 파일을 텍스트로 전환하여 첨부할 때
3) 웹 인증 (JWT, Basic Auth): HTTP Header에 인증 토큰이나 사용자 정보를 담아 보낼 때
```

1\. 장점과 한계
--------------
```
1) 장점:
 - 서로 다른 시스템 간에 데이터를 깨뜨리지 않고 교환할 수 있는 시스템 상호 운용성(System Interoperability) 및 전송 신뢰성 확보
 - 텍스트 전용 환경에서도 바이너리 데이터를 자유롭게 다룰 수 있음
2) 한계:
 - 용량 증가: 3바이트(24비트)를 4문자(32비트)로 표현하므로, 데이터 크기가 약 33% 증가함
 - 보안성 없음: 암호화(Encryption)가 아니라 단순 인코딩(Encoding)이므로 누구나 디코딩하여 원본을 볼 수 있음
```

1\. 변형: URL-Safe Base64
--------------
```
기본 Base64에 들어가는 +와 /는 URL에서 파라미터 구분자나 경로 구분자로 오인될 수 있습니다
이를 해결하기 위해 표준을 변형한 것이 URL-Safe Base64입니다.
    + -> - (하이픈)으로 대체
    / -> _ (언더바)로 대체
    끝의 = (패딩)은 생략하거나 URL 인코딩 처리
```

1\. 일반 바이너리 전송 vs Base64 인코딩 전송
--------------
```
구분          일반 바이너리 전송                          Base64 인코딩 전송
데이터 크기      원본 100% (작음)                        원본의 약 133% (크짐)
전송 안전성      텍스트 전용 시스템에서 데이터 훼손 위험 있음   어떤 시스템을 거쳐도 100% 안전함
주요 목적       "대용량 데이터, 바이너리 전용 통신"           "이메일 첨부, API 텍스트 데이터, 소형 내장 이미지"
```
