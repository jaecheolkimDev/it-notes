피드백 루프(Feedback Loop)
=============

1\. 개념
--------
개발 프로세스에서 코드를 작성한 후 결과가 눈에 보일 때까지의 시간을 피드백 루프라고 합니다.
```
기존 방식 (Hot Swap 없음):
코드 수정 ➔ 애플리케이션 종료 ➔ 빌드/컴파일 ➔ 서버 재시작 ➔ 로그인 및 이전 화면까지 직접 클릭해서 이동 ➔ 결과 확인 (소요 시간: 30초~2분)

Hot Swap 방식:
코드 저장(Ctrl + S) ➔ 1초 만에 실행 중인 화면/서버에 즉시 반영 (소요 시간: 0.1초~1초)
```

2\. 개발 생태계별 대표적인 적용 사례
--------
```
1) 프론트엔드: HMR (Hot Module Replacement)
웹 개발에서 가장 보편적으로 쓰이는 방식입니다. (Webpack, Vite, Next.js 등)
특징: 단순 페이지 전체 새로고침(Live Reload)과 다릅니다. 전체를 뒤엎는 게 아니라 변경된 모듈(파일)만 네트워크를 통해 브라우저로 쏘아 
     전달합니다.
강점 (State 유지): 모달창을 띄우거나 폼에 데이터를 잔뜩 입력해 둔 상태에서 CSS나 JS 코드를 수정해도, 입력해 둔 데이터나 화면 상태가 
                  날아가지 않고 해당 스타일/로직만 바뀝니다.

2) 백엔드 (Java / Spring Boot)
백엔드는 프론트엔드보다 핫 스왑이 조금 더 까다롭습니다. 메모리 구조상 클래스의 구조(메서드 추가, 필드 변경 등)가 크게 바뀌면 단순 교체가 
어렵기 때문입니다.
Spring Boot DevTools:   클래스 로더를 2개(기존 라이브러리용 Base ClassLoader + 작성 중인 코드용 Restart ClassLoader)로 나누어 
                        관리합니다. 코드가 바뀌면 작성 중인 코드 쪽 클래스 로더만 빠르게 버리고 다시 만들어 전체 재시작보다 훨씬 빠른 
                        속도로 반영합니다.
JRebel / DCEVM:         JVM 내부 깊숙이 개입하여 메서드 추가, 필드 수정, 어노테이션 변경까지 서버 재시작 없이 메모리에 즉시 
                        덮어씌우는 전문 생산성 도구입니다.
```

3\. 동작 원리
--------
[1. 파일 감지] ➔ [2. 증분 빌드] ➔ [3. 소켓 통신] ➔ [4. 런타임 교체]
```
1) File Watcher (파일 감지): 소스코드 파일의 변경(저장 이벤트)을 백그라운드 프로세스가 감지합니다.
2) Incremental Build (증분 빌드): 프로젝트 전체를 새로 빌드하지 않고, 수정된 파일 및 연결된 최소한의 파일만 콤팩트하게 컴파일합니다.
3) WebSocket / IPC 통신: 실행 중인 애플리케이션(브라우저, JVM, 앱)과 지속적으로 연결된 통신 채널을 통해 변경된 최신 바이트코드나 
                        모듈을 전달합니다.
4) Dynamic Swapping (런타임 교체): 런타임 엔진이 기존 메모리에 올라가 있던 옛날 코드를 새 코드로 메모리 주소 스위칭을 해버립니다.
```
