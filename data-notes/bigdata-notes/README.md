빅데이터 정리 노트
=================

1\. 개념
-------------------
```
빅데이터는 전통적인 데이터베이스 관리 도구나 데이터 처리 애플리케이션으로는 효과적으로 저장, 관리, 분석하기 어려운 대규모 데이터 집합을 의미합니다.
단순히 데이터의 크기만을 의미하는것이 아니라 데이터의 복잡성, 생성 속도, 다양한 형식 등을 포괄하는 개념입니다.

하나의 머신 안에서 처리할 수 없는 데이터가 빅데이터입니다.
```

2\. 3V (5V)
-------------------
```
1) Volueme  : 처리해야 할 데이터의 크기와 규모
2) Variety  : 다양한 형식(정형, 반정형, 비정형)과 구조의 데이터
3) Velocity : 데이터가 생성되고 처리되는 속도
4) Veracity : 정확성 (데이터의 신뢰성과 품질)
5) Value    : 가치 (데이터로부터 비즈니스 가치를 창출한다)
```

3\. OLTP(Online Transaction Processing) vs OLAP(Online Analytical Processing)
-------------------
```
1) OLTP : 짧고 빠른 실시간 트랜잭션 처리, 일상적인 비즈니스 운영을 지원하는 시스템입니다.
2) OLAP : 비즈니스 인텔리전스와(BI) 데이터 분석을 위한 시스템입니다.
3) 설계시 고려 사항
 3-1) OLTP, OLAP의 분리    : 무거운 분석 쿼리가 운영 시스템의 성능을 저하시키거나 실시간 트랜잭션 때문에 분석 작업이 방해받을 수 있습니다.
 3-2) 데이터 파이프라인      : OLTP 시스템에서 생성된 데이터를 분석과 집계를 위해서 OLAP로 이동시키는 파이프라인이 필요합니다. (ETL, ELT)
                            운영 데이터를 추출하고 변환하고 로드를 하게 됩니다.
 3-3) CDC(Change Data Capture) : 실시간성이 더 중요할때 사용한다.
                                 I/U/D를 실시간, 준실시간으로 감지해서 추출 후 전파하는 기술입니다.
                                 전체 데이터를 다시 읽지 않고 바뀐 것들만 잡아내서 보내줍니다.
                                 원본 DB의 데이터 변경 이벤트를 지속적으로 추적해서 다른 시스템으로 전달합니다.
```

4\. 하둡 (Hadoop)
-------------------
MapReduce랑 GFS(Google File System)를 오픈소스로 구현한 겁니다.
```
1) HDFS(Hadoop Distributed File System)
 1-1) 복사본의 배치 전략    : 첫 번째 복사본은 데이터를 쓰는 서버에
                           두 번째 복사본은 다른 랙의 서버에
                           세 번째는 두번째와 같은 랙의 다른 서버에 둡니다. (3개를 모두 다른 랙에 두면 네트워크 트래픽이 너무 많아집니다)
 * 랙 : 서버들이 묶인 단위
 1-2) NameNode (마스터 서버) : 어떤 파일들이 어떤 블록으로 구성되어 있고 각 블록이 어느 서버에 있는지를 기억하는 
                             일종의 전화번호부 같은 역할을 합니다. (HA를 통한 액티브 스탠바이 구조로 관리)
2) MapReduce(Data Locality) : 모든 데이터를 맵과 리듀스의 두 단계로 생각하자는 겁니다. 맵과 리듀스 사이에 셔플이라는 작업이 있음.
                              같은 키값을 가진 맵을 같은 리듀서로 보냅니다. 맵에서 디스크에 쓰고 리듀스는 디스크에서 다시 읽습니다.
```

5\. 스파크(Apoche Spark)
-------------------
```
1) RDD(Resilient Distributed Dataset)   : 분산처리를 하다가 서버가 죽어도 복구가 가능합니다. 한번 만들어지면 변경할 수 없습니다.
                                          Lazy하고 동작하면서 최적화를 진행합니다.
2) Memory   : 자주 사용하는 데이터를 메모리에 캐싱합니다. 스파크는 계산 과정을 기억했다가 필요하면 메모리에서 다시 계산합니다.
              메모리가 충분하면 스파크가 훨씬 빠릅니다.
* 하둡은 각 단계의 결과를 디스크에 저장해서 장애 복구를 합니다.
```

6\. 람다 아키텍처(Lambda Architecture)
-------------------
3개의 레이어로 구성
```
1) 배치 레이어   : 모든 데이터를 영구적으로 저장합니다. 배치를 돌려서 정확한 결과를 만들어냅니다. (하둡, 스파크 사용)
2) 스피드 레이어  : 실시간 처리를 하는 레이어입니다. 빠른 근사값을 제공합니다. (플링크나 카프카 스트림즈 같은 것들을 사용)
3) 서빙 레이어   : 배치 레이어와 스피드 레이어의 값을 합쳐서 제공합니다.
4) 장점
 4-1) 정확성과 빠른속도     : 배치로 정확한 결과를 보장하고 스트림으로 빠른 응답을 제공합니다.
 4-2) 장애에 강함          : 스피드 레이어가 죽어도 배치 레이어가 있기 때문에 조금 느려질 뿐 보정 이후 서비스는 계속됩니다.
 4-3) 데이터 재처리가 쉬움   : 뭔가 잘못됐으면 배치 레이어에서 전체 데이터를 다시 처리하면 됩니다.
5) 단점
 5-1) 복잡함               : 배치처리 시스템과 스트림처리 시스템, 총 2개의 완전히 다른 시스템을 동시에 운영해야 합니다. 
 5-2) 중복 코드 & 유지보수 어려움  : 같은 비즈니스 로직을 배치와 스트림에 2번 작성해야 합니다. (프레임워크가 다르기 때문에 코드 중복)
 5-3) 비용이 많이 듬
```

7\. 카파 아키텍처(Kappa Architecture)
-------------------
2개의 레이어로 구성
```
1) 스피드 레이어  : 스피드 레이어에서 다 처리한다. 재처리가 필요하면 카프카에 저장된 과거 데이터를 처음부터 다시 읽어서 처리한다.
2) 서빙 레이어   : 단일뷰만 제공한다.
3) 장점
 3-1) 단순함 & 빠름  : 하나의 처리 엔진만 관리한다.
 3-2) 코드 중복 없음  : 비즈니스 로직을 한번만 작성하면 된다.
 3-3) 비용 효율적
4) 단점
 4-1) 강력한 메시지 브로커 필요        : (카프카) 과거 데이터를 오래 보관하고 빠르게 리플레이, 재생을 할 수 있어야 합니다. 기술 요구사항이 높음.
 4-2) 매우 복잡한 배치 분석의 어려움 
 4-3) 재처리 시간
```
