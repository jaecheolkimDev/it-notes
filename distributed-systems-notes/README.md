분산 시스템(Distributed Systems)
================

1\. 경쟁 상태(Race Condition)
-----------------------------
두 개 이상의 프로세스나 서버가 공유 자원에 동시에 접근하여, 접근 순서에 따라 결과값이 달라지는 불안정한 상태를 말합니다.
```
실무 맥락: "서버 A와 B가 동시에 Redis에 접근해서 둘 다 배치를 실행해버렸다"면, 그 시스템은 Race Condition에 빠진 것입니다.

1) Check-Then-Act (확인 후 실행)     : 이 패턴은 어떤 조건이 참인지 확인한 후, 그 결과에 따라 동작을 수행하는 방식입니다.
    - 구조: if (condition) { doAction(); }
    - 문제점: 조건을 확인한 시점(Check)과 실제 동작을 수행하는 시점(Act) 사이에 시간적 간극(Race Window)이 존재합니다. 그 짧은 찰나에 
             다른 스레드가 조건을 변경해버리면, 이미 유효하지 않은 조건 위에서 동작이 실행되어 버립니다.
             
2) Read-Modify-Write (읽기-수정-쓰기)     : 이 패턴은 기존 상태를 읽어와서, 값을 변경한 뒤, 다시 저장하는 방식입니다.
    - 구조: count = count + 1; (또는 count++)
    - 문제점: 보기에는 한 줄의 코드지만, 실제 CPU 레벨에서는 1) 메모리에서 값을 읽고, 2) 값을 더하고, 3) 메모리에 쓰는 3단계로 나뉩니다.
    
3) 해결 방법    : 이러한 경쟁 상태를 방지하기 위해서는 여러 단계의 과정을 하나의 단위(Atomic)로 묶어야 합니다.
    - 동기화 (Synchronization): synchronized 키워드나 Lock을 사용하여 한 번에 한 스레드만 해당 블록에 접근하게 합니다.
    - 원자적 변수 (Atomic Variables): Java의 AtomicInteger, AtomicReference 등은 내부적으로 CAS(Compare-And-Swap) 알고리즘을 사용하여 
                                    하드웨어 수준에서 이 문제들을 해결합니다.
```

2\. Atomicity (원자성)
-----------------------------
"쪼개질 수 없는 하나의 단위"를 의미합니다. 여러 개의 단계(조회, 비교, 저장)가 중간에 끊기지 않고 전부 성공하든지, 전부 실패하든지 
둘 중 하나만 일어나야 한다는 원칙입니다.
```
실무 맥락: Check-then-Act를 해결하려면 '조회'와 '저장'을 하나의 Atomic Operation으로 합쳐야 합니다. (예: Redis의 SETNX)
```

3\. Idempotency (멱등성)
-----------------------------
연산을 여러 번 적용하더라도 결과가 달라지지 않는 성질입니다.
```
실무 맥락: 만약 중복 방지 로직이 실패해서 배치가 두 번 실행되더라도, DB 데이터가 두 번 쌓이지 않고 한 번만 반영되도록 로직을 짜는 것이 
'멱등한 설계'입니다.
```

6\. 중복성 (Redundancy)
-----------------------------
```
장애에 대비해 핵심 부품이나 서버를 여러 개 배치하는 것입니다. 
"1+1" 구조처럼 똑같은 자원을 하나 더 두어, 하나가 고장 나면 즉시 교체 투입될 수 있도록 설계하는 핵심 원리입니다.
```
