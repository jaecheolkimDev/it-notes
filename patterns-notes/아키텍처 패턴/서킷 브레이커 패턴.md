Circuit Breaker(서킷 브레이커) 패턴
=================

1\. 개념
-----------
```
MSA에서 특정 서비스에 문제가 발생했을 때 그 여파가 시스템 전체로 퍼지는 것을 방지하는 장벽 역할을 하는 설계 패턴입니다.
```

2\. 주요 작동 원리 (3가지 상태)
-----------
[ Closed ]  ---(에러율 초과)--->  [ Open ]
    ^                              |
    |                            (일정 시간 경과)
    |                              v
    +-----(성공)----- [ Half-Open ]
```
1) Closed (닫힘):
    정상적인 상태입니다. 모든 요청이 목적지 서비스로 전달됩니다.
    실패 횟수가 미리 설정한 임계치(Threshold)를 넘지 않으면 계속 이 상태를 유지합니다.

2) Open (열림):
    에러 발생률이 임계치를 넘으면 서킷 브레이커가 '열립니다'.
    이때부터는 요청을 목적지 서비스로 보내지 않고, 즉시 에러를 반환하거나 대체 로직(Fallback)을 실행합니다. 
    이를 통해 결함이 있는 서비스에 추가적인 부하를 주지 않고 대기 시간을 줄입니다.

3) Half-Open (반열림):
    서킷이 열린 후 일정 시간이 지나면 '반열림' 상태가 되어, 시스템이 회복되었는지 확인하기 위해 소량의 테스트 요청을 보냅니다.
    테스트가 성공하면 다시 Closed로 돌아가고, 실패하면 다시 Open 상태가 됩니다.
```

3\. 왜 사용하는가? (핵심 이점)
-----------
```
장애 전파 방지 (Cascading Failure)    : 하나의 서비스가 느려지거나 응답이 없으면, 그 서비스를 호출하는 다른 서비스들의 스레드도 함께 점유되어 
                                      시스템 전체가 마비될 수 있습니다. 서킷 브레이커는 이를 중간에 끊어줍니다.
빠른 실패 (Fail Fast)                : 응답을 받지 못할 서비스에 계속 요청을 보내며 기다리는 대신, 빠르게 실패를 선언하고 사용자에게 
                                      대체 화면을 보여줄 수 있습니다.
자동 복구 시도                        : 사람이 직접 개입하지 않아도 시스템 스스로 서비스의 상태를 체크하고 정상화되면 다시 연결을 재개합니다.
```

4\. 주요 라이브러리 (Java/Spring 생태계)
-----------
```
Resilience4j: 현재 Spring Cloud 환경에서 가장 표준적으로 사용되는 가볍고 유연한 라이브러리입니다.
```

5\. 샘플 코드
-----------
```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final ProductClient productClient;

    /**
     * @CircuitBreaker
     * - name: application.yml에 설정한 서킷 브레이커 이름
     * - fallbackMethod: 장애 발생(Open 상태) 시 대신 실행할 메서드 이름
     */
    @CircuitBreaker(name = "productService", fallbackMethod = "getProductFallback")
    public ProductDto getProductDetail(Long productId) {
        // External Service (상품 서비스) 호출
        return productClient.callProductApi(productId);
    }

    // Fallback 메서드 (원래 메서드와 반환 타입, 파라미터가 동일해야 하며 Throwable을 추가로 받음)
    public ProductDto getProductFallback(Long productId, Throwable t) {
        log.error("상품 서비스 호출 실패 (productId: {}), Reason: {}", productId, t.getMessage());
        
        // 먹통 대신 준비된 기본값이나 캐시 데이터를 반환 (Fail-Fast)
        return ProductDto.builder()
                .productId(productId)
                .name("임시 상품 정보")
                .price(0)
                .isAvailable(false)
                .build();
    }
}
```

6\. 샘플 설정 파일
-----------
```yml
resilience4j:
  circuitbreaker:
    instances:
      productService: # 서비스 이름
        slidingWindowType: COUNT_BASED       # 최근 N개 요청 기준으로 측정
        slidingWindowSize: 10               # 최근 10개의 요청을 감시
        minimumNumberOfCalls: 5            # 최소 5개 요청이 쌓인 시점부터 판별 시작
        failureRateThreshold: 50            # 실패율 50% 이상이면 Open (차단)
        waitDurationInOpenState: 10000ms    # Open 상태 유지 시간 (10초 후 Half-Open 전환)
        permittedNumberOfCallsInHalfOpenState: 3 # Half-Open 상태에서 시험삼아 보낼 요청 수
        automaticTransitionFromOpenToHalfOpenEnabled: true
```

7\. 샘플 코드 동작 순서
-----------
```
1) 정상 상황 (Closed): getProductDetail 실행 시 productClient.callProductApi()가 정상 호출됩니다.
2) 장애 발생: 최근 10번 중 5번 이상 실패하면 Open 상태로 전환됩니다.
3) 차단 및 Fallback: 회로가 열리면 외부 호출을 아예 시도조차 하지 않고 즉시 getProductFallback을 실행하여 0.001초 만에 대체 응답을 반환합니다.
4) 자동 복구 (Half-Open): 10초가 지나면 3번의 테스트 요청을 보내보고, 성공하면 다시 정상 상태로 복구됩니다.
```
