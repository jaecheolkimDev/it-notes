Spring 공부 노트
=================

```
OOP 패러다임을 가져간다는 의미는 객체들에게 적절한 책임과 역할을 부여하고, 
이 객체들이 서로 협력관계를 맺어 주면서 객체망을 형성해 나간다는 것입니다.
객체들은 서로 message를 주고 받으면서 협력을 해 나갈 수 있습니다. 
즉, 객체가 가지고 있는 책임을 수행해 주는 method를 호출 함으로써 message를 전달하는 것 입니다.
객체가 가지고 있는 책임들을 public하게 다른 객체에게 알려줄 수 있는 방법이 java에서 interface인 것입니다.
즉, 거대한 클래스, 거대한 메소드, 중첩된 if, else 문들로 뒤엉켜있는 스파게티 코드를 작성해 나가는 것이 아니라, 
적절한 객체를 식별해 내고 그 객체에서 적절한 행위를 할 수 있게 하라는 것입니다.
설계를 할 때 다양한 패턴을 사용하는 것 보다, 복잡한 상속 구조를 만들어 나가는 것보다, 
적절한 객체에게 절적한 책임과 역할을 부여해 나가는 것이 더 중요한 것 같습니다.
이렇게 설계된 객체망을 가지게 된다면 몇 가지 장점이 있습니다.
첫 번째는 테스트하기 쉬워집니다. 객체가 처리할 수 있는 message에 대해서, 즉 interface에 대해서만 테스트를 하면 되기 때문입니다.
객체와 협력관계를 맺고 있는 객체에 대해서는 mocking 처리를 하면 영향을 받지 않고 쉽게 단위 테스트를 작성 할 수 있습니다.
```

1\.개념
---------------
```
> 스프링 컨테이너 : 객체(Bean)를 생성·관리·소멸시키는 주체로, 프로그램 실행 중 객체의 생명주기를 대신 관리하는 공간.(IoC 엔진)
    → 대표 구현체는 BeanFactory 와 ApplicationContext
        > BeanFactory : 가장 기본적인 IoC 컨테이너로, Bean의 생성·조회·관리만 담당하는 단순한 객체 공장.

> IoC (Inversion of Control, 제어의 역전) : 객체의 생성과 의존성 관리의 제어권을 개발자가 아닌 스프링 컨테이너에게 위임하는 개념
- → 즉, 객체를 new로 직접 만들지 않고 스프링이 대신 생성하고 주입

> DI (Dependency Injection, 의존성 주입) : 객체 간의 의존 관계를 코드 내부에서 직접 연결하지 않고, 외부(컨테이너)가 주입해주는 방식
- → IoC를 구현하는 구체적인 방법이며, IoC의 하위 개념
  - ex) @Autowired

> Bean : 스프링 컨테이너에 의해 관리되는 객체(인스턴스)
- → @Component, @Service, @Repository, @Controller 등의 어노테이션이나 @Bean 메서드로 등록됨

> 스프링 컨텍스트(Spring Context) : 스프링의 전체 실행 환경을 지칭하는 포괄적인 개념

> Application Context : BeanFactory의 확장판으로, Bean 관리 + 환경 설정, 메시지 처리, 이벤트 발행, AOP 지원 등을 함께 제공하는 스프링의 핵심 컨테이너

> AOP (Aspect Oriented Programming, 관점 지향 프로그래밍) : 핵심 로직(Core Concern) 과 공통 로직(Cross-cutting Concern) 을 분리하여,
  공통 기능을 횡단 관심사(Aspect) 로 관리하는 방식
    → 예: 로깅, 트랜잭션, 보안 처리 등
    > 횡단 관심사 : 여러 서비스에서 공통적으로 쓰이는 것
    > AOP를 사용하지 않으면 모든 메서드마다 session.beginTransaction(), commit(), rollback() 같은 코드를 직접 작성해야 합니다.
      하지만 AOP를 적용하면 "이 메서드는 트랜잭션 안에서 실행되어야 해"라는 설정만으로 트랜잭션 처리를 외부에서 주입할 수 있습니다.
    > 스프링은 AOP를 구현하기 위해 프록시 패턴을 사용합니다. 
      우리가 @Transactional이 붙은 빈을 호출할 때, 스프링은 원본 객체 대신 이를 감싸고 있는 프록시 객체를 주입해 줍니다.

> POJO (Plain Old Java Object) : 스프링이 관리하는 Bean의 기본 형태로, 특정 프레임워크에 종속되지 않은 순수 자바 객체
- → 스프링은 POJO에 IoC, DI, AOP를 적용해 유연한 구조를 제공함



> PSA(Portable Service Abstraction)
 : "환경과 세부 기술에 변화에 관계없이 일관된 방식으로 기술에 접근할 수 있게 해주는 추상화 계층"을 의미합니다.
    즉, 부가 기능이 어떤 하위 기술(JDBC, JPA 등)로 구현되든 일관된 방식(What)으로 사용할 수 있게 해주는 설계 원칙.
    
    1. PSA의 핵심 개념: "잘 만든 인터페이스"
        PSA의 핵심은 특정 기술에 종속되지 않도록 추상화(Abstraction) 계층을 두는 것입니다.
        예를 들어, 서비스에서 트랜잭션을 처리할 때 JDBC를 쓸 수도 있고, JPA나 Hibernate를 쓸 수도 있습니다. 
        만약 PSA가 없다면 기술을 바꿀 때마다 비즈니스 로직의 코드를 다 수정해야 합니다. 
        하지만 스프링은 이를 인터페이스로 한 번 감싸서 제공하기 때문에, 우리는 내부 구현이 바뀌어도 똑같은 방식으로 코드를 작성할 수 있습니다.
    
    2. PSA의 대표적인 사례
        스프링을 사용하면서 우리도 모르게 이미 많은 PSA를 사용하고 있습니다.
        
        ① 트랜잭션 PSA (PlatformTransactionManager)
            가장 대표적인 예시입니다.
            
            JDBC 기반: DataSourceTransactionManager
            JPA 기반: JpaTransactionManager
            Hibernate 기반: HibernateTransactionManager
            
            사용자 코드: 어떤 기술을 쓰든 @Transactional 하나로 해결됩니다.
            내부적으로는 PlatformTransactionManager라는 인터페이스를 통해 일관된 방식으로 트랜잭션을 관리하기 때문입니다.
        
        ② 스프링 웹 MVC (@Controller, @RequestMapping)
            우리는 서블릿(Servlet) 기반의 톰캣(Tomcat) 위에서 구동되는 코드를 짜지만, 
            정작 코드 어디에도 HttpServlet을 상속받거나 로우 레벨의 서블릿 API를 직접 다루는 일은 거의 없습니다. 
            스프링이 웹 기술을 추상화해두었기 때문입니다. 
            덕분에 나중에 서버를 네티(Netty) 기반의 WebFlux로 바꿔도 프로그래밍 모델은 거의 그대로 유지됩니다.
        
        ③ 캐시(Cache) PSA (@Cacheable)
            데이터를 Redis에 저장하든, Ehcache나 Caffeine에 저장하든 개발자는 @Cacheable이라는 추상화된 애노테이션만 사용하면 됩니다. 
            설정 파일에서 어떤 캐시 구현체를 사용할지만 바꿔 끼우면 로직 수정 없이 기술 변경이 가능합니다.
    
    3. PSA가 주는 이점
        유연한 기술 교체: 새로운 기술이 나와도 비즈니스 로직을 수정할 필요가 거의 없습니다.
        테스트 용이성: 실제 DB나 외부 시스템 대신 테스트용 가짜 객체(Mock)로 추상화 계층을 갈아 끼우기 쉬워져 단위 테스트가 편해집니다.
        낮은 결합도: 특정 프레임워크나 라이브러리에 내 코드가 종속되지 않습니다.
    
    요약
        프록시/데코레이터 패턴: 트랜잭션 같은 부가 기능을 어떻게(How) 비즈니스 로직과 분리하여 적용할 것인가에 대한 구조적 해답.
        이 두 가지가 합쳐져서 스프링은 "비즈니스 로직은 기술적 환경에 구애받지 않고 순수하게 유지되어야 한다(POJO)"는 철학을 실현합니다.
```


2\. 처리 순서
------------------
```
사용자의 요청이 들어오면 Filter(대문) → Interceptor(현관문) → AOP(방 문) 순서로 거쳐간다고 이해하시면 됩니다.
- 필터               : 서블릿 컨테이너(Tomcat) 레벨에서 동작합니다.
- 인터셉터            : 스프링 컨텍스트(Spring Context) 내부에서 동작합니다.
- AOP               : 컨트롤러뿐만 아니라 서비스(Service)나 컴포넌트 메서드가 호출될 때 그 앞뒤를 가로챕니다.
- ControllerAdvice  : 컨트롤러에서 발생하는 예외(Exception)나 응답 데이터를 가로챕니다.
```


3\.스프링 부트
------------------
```
스프링(Spring)은 자바 애플리케이션 개발을 위한 핵심 프레임워크이며,
스프링 부트(Spring Boot)는 이 스프링 프레임워크를 기반으로 복잡한 설정을 자동화하고 개발 편의성을 높여, 빠르고 쉽게 웹 애플리케이션을 만들 수 있도록 도와주는 도구(framework)입니다.
스프링 부트는 스프링의 다양한 라이브러리(의존성) 관리와 설정을 '자동화'하고,
'내장 서버'를 제공하여 WAS 없이 단독으로 실행 가능하게 만들어 개발자가 설정보다는 비즈니스 로직에 집중할 수 있게 합니다. 
```


4\. Bean
------------------
```
1) 빈 이벤트 라이프사이클 : 스프링 컨테이너 생성 -> 스프링 빈 생성 -> 의존관계 주입 -> 초기화 콜백 -> 사용 -> 소멸 콜백 -> 스프링 종료
2) 인터페이스 InitializingBean 상속하여 afterPropertiesSet 메서드를 재정의하여 스프링 빈 생명주기를 관리하는 방법이 있다.
    - afterPropertiesSet 메서드는 의존관계 주입이 되고나서 호출된다.
```
