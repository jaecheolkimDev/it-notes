벡터 DB
======================


1\. 일반 DB와 차이점
--------------
```
일반적인 데이터베이스(MySQL, Oracle 등)는 '글자(텍스트)'나 '숫자'가 정확히 일치하는지 찾아냅니다.
하지만 AI 시대에는 "단어의 의미나 맥락이 비슷한 것"을 찾아야 할 때가 많습니다.

컴퓨터가 단어의 의미를 이해할 수 있도록 길고 복잡한 숫자 배열(이것을 벡터/Embedding라고 합니다)로 바꾸어 저장하고, "의미가 가장 유사한 데이터"를 
빠르게 찾아주는 창고 역할을 하는 것이 바로 벡터 DB입니다.
```

2\. 임베딩 벡터 저장 (Storage)
--------------
```
메모리나 디스크에 임베딩된 고차원 배열(예: 1536차원의 float 배열)을 효율적으로 저장하는 공간이 필요합니다. 
자바로 치면 Map<String, float[]> 구조를 디스크 파일 시스템이나 메모리에 최적화하여 압축 저장하는 포맷입니다.
```

3\. 고속 검색을 위한 '인덱싱(Indexing)' 알고리즘
--------------
Vector DB 구현의 핵심이자 기술력의 중추입니다. 데이터를 그냥 쌓아두는 게 아니라, 검색하기 좋은 '구조'로 가공합니다.
```
가장 유명한 알고리즘 두 가지는 다음과 같습니다.
1) HNSW (Hierarchical Navigable Small World): 현재 가장 많이 쓰이는 그래프 기반 알고리즘입니다. 벡터들을 서로 거리가 가까운 것끼리 선으로 연결해 
    둡니다. 거대한 지도에서 '대도시 ➡️ 소도시 ➡️ 우리 동네' 순으로 찾아가듯, 상위 레이어에서 크게 건너뛰며 가다가 목적지 근처에서 촘촘하게 링크를 타고
    들어가 가장 유사한 벡터를 찾습니다.
2) IVF (Inverted File Index): 전체 벡터 공간을 K-Means 클러스터링 같은 알고리즘으로 여러 개의 방(Cluster)으로 나눕니다. 질문이 들어오면 
    "이 질문은 3번 방이랑 가장 가깝네?"라고 판단한 뒤, 3번 방 안에 있는 벡터들과만 유사도를 계산합니다. 전체를 다 뒤질 필요가 없어 속도가 빠릅니다.
```

4\. 유사도 측정 엔진 (Distance Metrics)
--------------
두 벡터가 얼마나 닮았는지 계산하는 수학적 연산기입니다.
```
1) 코사인 유사도(Cosine Similarity): 벡터의 크기(길이)와 상관없이 '방향'이 얼마나 일치하는지 파악 (RAG에서 가장 흔히 씀)
2) 내적(Dot Product): 벡터의 방향과 크기를 모두 고려 (임베딩 모델이 정규화되어 있을 때 매우 빠름)
3) 유클리드 거리(L2 Distance): 다차원 공간에서 두 점 사이의 절대적인 직선거리
```

5\. 종류
--------------
```
1) Chroma   : 오픈소스 벡터 데이터베이스
 - 내장형(In-memory)으로 실행할 수 있음
2) Pinecone : 클라우드에서 다 알아서 해주는 서비스(SaaS)

비교 항목   🟢 Chroma (크로마)                      🌲 Pinecone (파인콘)
형태      오픈소스 (내 서버에 설치)                 완전 관리형 클라우드 서비스 (SaaS)
비용      100% 무료                                 무료 티어 제공 + 사용한 만큼 결제
초기 설정   pip install chromadb 끝 (매우 간편)      "회원가입, API 키 발급, 인덱스 생성 필요"
적합한 규모  "프로토타입, 소규모 프로젝트, 로컬 테스트"   "대규모 서비스, 대용량 데이터, 실제 상용화"
서버 관리   데이터가 커지면 서버 사양 등 직접 관리 필요   "데이터가 기가바이트(GB), 테라바이트(TB)로 커져도 클라우드가 자동 스케일링"

Chroma를 고르는 상황:
    "지금 당장 내 노트북에서 RAG 기능 작동하는지 가볍게 PoC(개념 검증)를 해보고 싶다."
    "회사 내부 보안 규정 때문에 데이터를 외부 클라우드(Pinecone)에 올리면 안 되고, 무조건 사내 서버 안에서 해결해야 한다."

Pinecone을 고르는 상황:
    "실제 사용자들이 쓸 프로덕션(상용) 서비스를 출시해야 한다."
    "문서 양이 너무 많아서 내 서버 메모리로는 감당이 안 되고, 속도가 무조건 안정적이고 빨라야 한다."
    "DB 인프라 관리나 모니터링에 손 쓰기 싫고, 오직 서비스 개발에만 집중하고 싶다."
```
