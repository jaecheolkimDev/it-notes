SW 아키텍처 공부 노트
=================

1\. 개요
----------------------------------------
```
사상(Philosophy)          : "시스템을 어떻게 분리하고 연결할 것인가?"에 대한 철학입니다. (예: "모든 걸 하나로 합치자" vs "잘게 쪼개자")
트레이드오프(Trade-off)     : 모든 아키텍처는 완벽하지 않습니다. 아키텍처 패턴을 선택한다는 것은 특정 이점(확장성 등)을 얻기 위해 특정 비용
                            (복잡성 등)을 지불하기로 결정하는 의사결정 과정입니다.
```

2\. 아키텍처를 결정짓는 핵심 원리
----------------------------------------
```
관심사의 분리 (Separation of Concerns, SoC) : 소프트웨어의 기능을 중복되지 않게 각기 다른 영역으로 나누는 것.
응집도와 결합도 (Cohesion and Coupling)     : 모듈 내부 요소들이 얼마나 밀접한지(높은 응집도), 
                                           모듈끼리 얼마나 의존하는지(낮은 결합도)를 조절하는 것.
추상화 (Abstraction)                       : 복잡한 내부 로직은 감추고 인터페이스만 노출하여 소통하는 것.
```

3\. 종류
----------------------------------------
```
1) Monolithic Architecture : 소프트웨어의 모든 구성요소가 한 프로젝트에 통합되어있는 형태.
    - 아직까지는 많은 소프트웨어가 Monolithic형태로 구현되어 있고, 소규모에서는 훨씬 합리적이다.
    - 간단한 Architecture이고, 유지보수가 용이하기 때문.
      [단점]
        - 서비스/프로젝트가 커지면 커질수록, 영향도 파악 및 전체 시스템 구조의 파악에 어려움이 있다.
        - 빌드 시간 및 테스트시간, 그리고 배포시간이 기하급수적으로 늘어난다.
        - 서비스를 부분적으로 scale-out하기가 힘들다.
        - 부분의 장애가 전체 서비스의 장애로 이어지는 경우가 발생한다.
    
2) SOA (Service Oriented Architecture, 서비스 지향 아키텍처)
    시스템의 기능을 비즈니스 단위의 '서비스'로 잘게 쪼개어 구축합니다. 이 서비스들은 네트워크를 통해 서로 통신합니다.

3) MSA(Micro Service Architecture)
- 하나의 큰 어플리케이션을 여러개의 작은 어플리케이션으로 쪼개어 변경과 조합이 가능하도록 만든 아키텍쳐.
- 서비스/프로젝트가 크고, 복잡하고, 장기적으로 운영될 수록, MSA의 장점이 더욱 드러난다.
  MSA는 큰 의미에서 SOA의 부분집합으로 여겨지고 있다.
    * small services, each running in its own process
    * independently deployable
```
