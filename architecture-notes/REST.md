REST(Representational State Transfer) 공부 노트
=================

1\. 개요
---------------
```
사상(Philosophy)          : "시스템을 어떻게 분리하고 연결할 것인가?"에 대한 철학입니다. (예: "모든 걸 하나로 합치자" vs "잘게 쪼개자")
트레이드오프(Trade-off)     : 모든 아키텍처는 완벽하지 않습니다. 아키텍처 패턴을 선택한다는 것은 특정 이점(확장성 등)을 얻기 위해 특정 비용
                            (복잡성 등)을 지불하기로 결정하는 의사결정 과정입니다.
```

2\. REST의 6가지 설계 원칙 (Constraints)
---------------
단순히 GET, POST를 쓴다고 RESTful한 것은 아닙니다. 아래 6가지를 충족해야 진정한 REST입니다.
```
1) Uniform Interface (일관된 인터페이스): 자원(URI)은 고유해야 하며, 표준 HTTP 메소드를 통해 조작되어야 합니다. (가장 중요)
2) Stateless (무상태성): 서버는 클라이언트의 상태(세션 등)를 보관하지 않습니다. 각 요청은 그 자체로 필요한 모든 정보를 포함해야 하며, 
                       이는 서버의 확장성을 극대화합니다.
3) Cacheable (캐시 가능성): HTTP의 기존 인프라(캐시)를 그대로 활용하여 네트워크 부하를 줄여야 합니다.
4) Client-Server 구조: 서버는 데이터를 제공하고, 클라이언트는 UI/사용자 경험에 집중하여 양측이 독립적으로 발전할 수 있어야 합니다.
5) Layered System (계층화 시스템): 클라이언트는 서버와 직접 통신하는지, 중간에 프록시나 로드밸런서가 있는지 몰라도 통신에 지장이 없어야 합니다.
6) Code on Demand (선택 사항): 서버가 클라이언트에게 실행 가능한 코드(JS 등)를 보내 기능을 확장할 수 있습니다.
```

3\. 리소스(Resource) 중심의 설계 규칙
---------------
```
항목        나쁜 예 (RPC 방식)       좋은 예 (REST 방식)
URI        /getUserInfo?id=102    /users/102
메소드POST  /updateUserPUT         /users/102
자원 식별   자원 이름에 동사가 포함됨  자원은 명사로, 행위는 HTTP 메소드로 표현
```

4\. 실무에서 가장 놓치기 쉬운 점: HATEOAS
---------------
진정한 REST의 정수는 HATEOAS(Hypermedia As The Engine Of Application State)입니다.
```
개념: 응답 데이터 속에 다음에 할 수 있는 행위에 대한 링크를 포함하는 것입니다.
효과: 클라이언트는 서버의 URI 구조를 미리 다 알 필요가 없습니다. 서버가 주는 링크를 따라가기만 하면 되므로, 서버의 경로가 바뀌어도 
     클라이언트 코드는 깨지지 않습니다. (높은 디커플링)
```

5\. RESTFUL
---------------
```
해당 URL만 보더라도 바로 어떤 작업을 하는지를 알 수 있도록 하나의 데이터는 하나의 URL을 갖도록 작업하는 방식
```

6\. Request 전송 방식
---------------
```
- Get 방식 : URL의 쿼리문자열에 데이터를 같이 전달하는 방식으로 데이터 길이에 제한이 있고, 보안에 취약하다.
- POST 방식 : 헤더에 데이터를 넣어 보내기 때문에 보안에 조금 더 유리하고 데이터 길이에 제한이 없다. 하지만, Get에 비해 다소 느리다.
- DELETE 방식 : RESTFUL에서 삭제 기능을 할 때 주로 사용된다.
- PUT/PUSH 방식 : RESTFUL에서 수정 작업을 할 때 주로 사용된다.
```
